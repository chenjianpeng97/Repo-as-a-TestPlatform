# 基于AI的自动化测试工程实践

## AI实现自动化难点

- 人员能力要求并不算低[[授权查询.feature]]需讲透业务+表实现，这部分**胶水代码**的实现类似**70%**左右的后端难度，只靠AI+MCP无法写出
- AI+MCP能写出的，简单列表查询是否报错，导出是否成功等；涉及复杂断言仍需人工配合AI写出
- 复杂用例需要设计能力，如取舍如何断言权限校验方案，全量数据比较 or SQL查询对比页面/接口返回数量值；如何决策数据驱动，实时从sql读取/写死测试用例数据；根据难度取舍覆盖自动化性价比

## 实施方向

- 新项目中，建立测试准入机制，划分模块冒烟用例，自动化这些高层次易实现的，统计冒烟测试自动化率；由于目前设计上同时生成接口和UI层，冒烟测试在UI不稳定情况下可不作为质量门禁,以接口冒烟自动化通过率为基准
- 老项目中，抽取重点功能，如数据权限，覆盖**回归测试**，统计回归测试自动化率
- 形成自动化代码后需团队支持经常运行这些自动化，达到自动化代码的收益最大化，统计**自动化稳定性**
- 新测试工程师进入自动化任务时，应充分培训，分开用例书写任务和steps实现任务，监控其自动化代码质量，形成自动化代码质量的闭环

## 目标达成

- **工程化**: [[README.md]]文档描述了仓库结构
- **工程化**：引入gherkin+behave驱动，使得用例编写任务和自动化实现任务分离，方便根据代码能力分配用例编写和steps实现任务
- **规范化**：自动化用例规范化->引入gherkin语法统一自动化执行用例和自然语言描述用例，且为纯文本格式，方便cursor建立索引，形成知识复利
- **规范化**：代码Lint,用Ruff+GitlabCI (暂未达成)
- **规范化**：见[[README.md]]中的SKILL LIST,通过skill规范feature用例风格，api/ui object知识沉淀方案，自动化建立标准流程
- **替代能力**: 见实施方向，新老项目通过自动化逐步替换**回归测试**和**冒烟测试**,通过替代率来量化自动化收益
- **替代能力**: 通过统计用例执行测试，发现缺陷/回归拦截次数来量化自动化收益
